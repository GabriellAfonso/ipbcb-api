# Implementation Plan: Members Management for Church Leaders

**Branch**: `010-members-management` | **Date**: 2026-09-25 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/010-members-management/spec.md`

## Summary

Add leader-only routes under `/api/admin/members/` for listing, reading, creating, editing and
deleting members, managing a leader-only photo, reading an edit history, and fetching picker
options. Three new services (`MemberRosterService`, `MemberPhotoService`,
`MemberChangeLogService`) sit on three new ports (`MemberRosterRepository`,
`MemberChangeLogRepository`, `MemberPhotoStorage`). History rows come from a pure diff of
before/after snapshots, written in the same `transaction.atomic` as the edit. Photo files are
written before the transaction and old ones deleted in `on_commit(robust=True)`. One additive
migration: `Member.photo` + `MemberChangeLog`. The existing member list and birthdays are
untouched.

## Technical Context

**Language/Version**: Python 3.14, `.venv_windows`

**Primary Dependencies**: Django 6, DRF, dependency-injector, Pydantic, Pillow (via
`core.files.image_validation`). No new dependency.

**Storage**: PostgreSQL (one additive migration); filesystem `MEDIA_ROOT/members/` via
`default_storage`.

**Testing**: pytest + pytest-django, DRF `APIClient` with the `conftest` helpers
(`make_auth_client`, `make_member_client`), `override_settings(MEDIA_ROOT=tmp_path)`,
`django_capture_on_commit_callbacks`, named fakes (`FakeMemberRosterRepository`,
`FakeMemberChangeLogRepository`, `FakeMemberPhotoStorage`, `FixedClock`), mypy, ruff, bandit.

**Target Platform**: Linux container behind nginx, prefix `/ipbcb/`.

**Project Type**: Web service (REST API), single Android client.

**Performance Goals**: Leader list for 1,000 members in one request, constant query count
(`select_related("status")`, no per-row queries). Record: 3 queries max (row + status/role
join, ministries prefetch). History: one query with `select_related("editor__profile")`.

**Constraints**: No signals. No cross-feature imports. Member data never in logs. No change to
`/api/members/` or birthdays responses.

**Scale/Scope**: One congregation, hundreds of members, a handful of leaders.

## Technical Decisions

Full reasoning in [research.md](research.md).

- **D-1** Service owns `transaction.atomic` + `on_commit` (R-01). Service tests are
  `django_db` with fakes.
- **D-2** History = pure `diff_member_records(before, after)` on `MemberRecordDTO` snapshots,
  text via `render_history_value` (R-02).
- **D-3** `MemberPatchDTO.model_fields_set` separates "not sent" from "sent null" (R-03).
- **D-4** Serializer checks shape; service checks existence and date rules with an injected
  `Clock`; Portuguese messages naming the value (R-04).
- **D-5** Photo: validate → save file → atomic(row + history + `on_commit(delete old,
  robust=True)`) → on failure delete the new file (R-05).
- **D-6** `MemberPhotoStorage` Protocol over `default_storage` (R-06).
- **D-7** Editor name from `editor__profile__name`, fallback username (R-07).
- **D-8** Reuse `IsAdminUser` (spec FR-001, user decision).
- **D-9** One log line per write: `member_id`, `editor_id`, `changed_fields` count (R-09).
- **D-10** Three services / three ports, existing `MemberService` untouched (R-11).

## Open question for the user

- **R-12 Django admin bypass.** Edits/deletes through `/ipbcb/admin/` write no history and a
  delete there orphans the photo file. Plan default: leave as is and document it in
  `specs/members/spec.md`. Alternatives: `Member` read-only in the admin, or unregistered.

## Implementation Order

Each step leaves the tree consistent for the mypy pre-commit hook (it checks the whole tree).

1. **Specs** (done in `/speckit-specify`): `specs/members/spec.md`, constitution sensitive-data
   rule. Add the R-12 outcome to the domain spec.
2. **`core`**: `MemberNotFoundError`. Test: handler maps it to 404 `NOT_FOUND` with the id in
   `detail`.
3. **Model + migration**: `Member.photo`, `is_active` comment, `MemberChangeLog`;
   `makemigrations`. Tests: `__str__` has no member data,
   ordering, CASCADE on member delete, SET_NULL on editor delete.
4. **Domain rules + DTOs**: `features/members/domain/member_changes.py` (diff, render),
   `member_dates.py` (future / baptism-before-birth). Pure unit tests, parametrized over every
   field type and the ministries ordering.
5. **Ports + implementations**: Protocols in `repositories/interfaces.py`;
   `MemberRosterRepositoryImpl`, `MemberChangeLogRepositoryImpl`,
   `DefaultStorageMemberPhotoStorage`. Integration tests: query counts
   (`django_assert_num_queries`), ordering, missing-id lookups, storage on `tmp_path`.
6. **Services**: `MemberRosterService`, `MemberPhotoService`, `MemberChangeLogService` with
   fakes: history rows per case (create, change, unchanged, ministries, clear), rollback leaves
   no history, photo ordering and cleanup incl. failure paths, log `extra` keys.
7. **Serializers, views, URLs, DI**: `serializers/admin_member_serializers.py`,
   `views/admin_members.py`, `views/admin_member_photo.py`, `views/admin_member_history.py`,
   routes in `features/members/urls.py`, providers + wiring in `config/di.py`. Integration
   tests: every contract route × (401, 403 member, 403 no profile, 404, 200/201/204), 304 +
   cache headers, unknown keys rejected, non-object body 400, photo 403 for non-leaders through
   the media route, regular list/birthdays regression (is_active filter, id+name only).
8. **Validation**: quickstart §1–§3.
