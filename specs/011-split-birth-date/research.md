# Research: Split Member Birth Date

Decisions for [spec.md](spec.md). Every item builds on what feature 010 already put in place
(`specs/010-members-management/research.md`); only what changes is written here.

---

## R-01 Column type and database constraints

**Decision**: three `PositiveSmallIntegerField(null=True, blank=True)` columns
(`birth_day`, `birth_month`, `birth_year`) plus `Meta.constraints` with three
`CheckConstraint`s:

- `member_birth_day_month_together`: `birth_day` and `birth_month` both null or both not null;
- `member_birth_day_range`: `birth_day` null or 1-31;
- `member_birth_month_range`: `birth_month` null or 1-12.

`PositiveSmallIntegerField` already rules out 0 and negatives for the year at the database
level on PostgreSQL (`CHECK >= 0`); the "at least 1" and "not after the current year" rules
stay in the domain function (R-03), since "current year" moves and cannot live in a constraint.

**Rationale**: the Django admin still edits `Member` without the service (spec 010, known
limitation). Django 6 runs `Model.validate_constraints()` inside the admin form's `full_clean`,
so these constraints show up there as form errors instead of letting the admin store a day
without a month, which would silently break the birthdays list. Calendar validity (31/04) and
the future/baptism rules are not expressible as simple checks and stay service-only; the admin
limitation remains documented for those.

**Alternatives considered**:
- No constraints, service validation only — leaves the admin able to write half pairs.
- `Model.clean()` calling the domain function — makes the model import the domain module and
  runs "today" from the model; rejected to keep the model a plain entity (CLAUDE.md §2).
- Remove `Member` from the admin — larger decision already left open in 010 (R-12); not
  re-opened here.

## R-02 Migrations: three steps

**Decision**:

1. `0004_…` — generated by `makemigrations`: add the three columns and the constraints. All
   existing rows have three nulls, which satisfies every constraint.
2. `0005_split_birth_date` — hand-written data migration (allowed by CLAUDE.md §5), reason
   at the top of the file. One `UPDATE` through the historical model:
   ```
   filter(birth_date__isnull=False).update(
       birth_day=ExtractDay("birth_date"),
       birth_month=ExtractMonth("birth_date"),
       birth_year=Case(When(birth_date__year=1, then=Value(None)),
                       default=ExtractYear("birth_date")),
   )
   ```
   `RunPython(forward)` with **no** `reverse_code`, so `migrate members 0004` raises
   `IrreversibleError` (spec FR-015).
3. `0006_…` — generated by `makemigrations`: remove `birth_date`.

**Rationale**: a single set-based `UPDATE` touches every row in one statement, with no Python
loop and no query per row (constitution, Data Integrity). `ExtractYear`/`ExtractDay` work on
PostgreSQL (production) and SQLite (tests). Year 1 is the only placeholder value (spec
Assumptions).

**Alternatives considered**:
- Python loop + `bulk_update` — same result, more code, more memory; no benefit at this size.
- `RunPython.noop` as reverse — would "succeed" and leave members without any birth data after
  a rollback; worse than refusing.
- One migration mixing schema and data — `makemigrations` would not generate it, and a failed
  data step would leave schema half applied on databases without transactional DDL.

**Deploy**: all three ship in the same deploy (user decision, plan D-8).

## R-03 Validation rules as one pure function

**Decision**: `features/members/domain/member_dates.py` gets a frozen dataclass
`BirthDateParts(day, month, year)` and `validate_member_date_parts(birth: BirthDateParts,
baptism_date, today)` replaces `validate_member_dates`. Checks, in order, each raising the
existing domain `ValidationError` with the offending value and the expected shape, in
Portuguese (the existing convention — the message reaches the leader's screen):

1. range: day 1-31, month 1-12, year 1-9999;
2. pair: day and month both set or both empty;
3. calendar: `day <= calendar.monthrange(year or 2000, month)[1]` — 2000 is a leap year, so
   29/02 passes without a year and fails with a non-leap one;
4. future: `year > today.year`; full date `date(year, month, day) > today`;
5. future baptism (unchanged);
6. baptism before birth: full date vs `baptism_date`; year only vs `baptism_date.year`;
   nothing with day+month only.

Example message: `"Dia de nascimento sem mês: birth_day=12, birth_month=None. Envie os dois
ou nenhum."`

**Rationale**: every rule lives in one pure, clock-injected function, as today. Ranges are
checked here, not by `IntegerField(min_value=…)` in the serializer, because DRF's default
messages omit the offending value (CLAUDE.md §8). The 9999 upper bound only protects
`date(...)` from overflowing; the real upper bound is the current year (rule 4).

**Alternatives considered**: `calendar.isleap` special-case for 29/02 — `monthrange` with a
leap fallback covers every month in one expression.

## R-04 Patch merge

**Decision**: `MemberRosterService._check_patch` builds `BirthDateParts` from the sent parts,
falling back to the stored `before` value for each part not sent (`model_fields_set`, as for
`birth_date` today). The merged value is what gets validated.

**Rationale**: spec FR-006 — sending only `birth_day` is checked against the stored month.

## R-05 Serializer and DTOs

**Decision**: `birth_date` is replaced by three `serializers.IntegerField(required=False,
allow_null=True)` in `MemberPatchSerializer` (inherited by `MemberCreateSerializer`) and three
`IntegerField(allow_null=True)` in `MemberRecordSerializer`. `MemberRecordDTO`,
`MemberCreateDTO`, `MemberPatchDTO` get `birth_day/birth_month/birth_year: int | None`.
`_PATCH_COLUMNS` in the roster repository lists the three new names. A request still sending
`birth_date` is rejected by the existing unknown-key check (no compatibility, spec FR-008).

## R-06 History

**Decision**: `HISTORY_FIELDS` lists `birth_day`, `birth_month`, `birth_year` in place of
`birth_date`. `render_history_value` gains an `int` branch after the `bool` one (`bool` is an
`int` subclass) returning `str(value)`; `HistoryValue` gains `int`. `MemberChangeLog.field`
(`max_length=32`) fits the new names. Stored `birth_date` rows are untouched: the history
endpoint returns rows as stored, it does not look `field` up in `HISTORY_FIELDS`.

## R-07 Birthdays repository

**Decision**:
```
Member.objects.filter(is_active=True, birth_day__isnull=False,
                      birth_month__gte=start, birth_month__lte=end)
    .order_by("birth_month", "birth_day")
    .values_list("name", "gender", "birth_month", "birth_day")
```
The `ExtractMonth`/`ExtractDay` annotations go away. `birth_day` not null implies
`birth_month` not null (R-01 constraint), so one null check is enough. Response shape and
`BirthdayDTO` unchanged.

## R-08 Seed command

**Decision**: `FAKE_MEMBERS` becomes `(name, gender, day, month, year)`; the existing 30 keep
their dates, plus three new entries: day+month only, year only, nothing (spec FR-018). The
`--clear` path is unchanged (deletes by name).

## R-09 Verifying against the production dump

**Decision**: before the deploy, restore the dump locally, record
`(id, birth_date)` for every member, run `migrate members`, and compare with a query that
must return zero rows (quickstart §2). Checked: day/month equal; year equal unless it was 1;
year null exactly when it was 1; no member gained or lost a date.
